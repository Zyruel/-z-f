# [z]f — come è fatto

Questo file è per chi legge o modifica il codice: come funziona ogni parte, le scelte tecniche e
le misure. Per usare [z]f basta il [README](../README.md); le regole dell'interfaccia sono in
[`DESIGN.md`](DESIGN.md), cosa cambia in ogni versione in [`NOVITA.md`](../NOVITA.md).

## Nome tecnico

**[z]f** è il nome dell'applicazione. Dove le parentesi quadre darebbero problemi (file, cartelle,
registro, nomi interni di Windows) il nome tecnico è **z-f**: `z-f.exe`, `%APPDATA%\z-f`,
`z-f-log.txt`; nel codice C++ gli identificatori sono `ZF_...`. Fino alla 0.15 si chiamava zx:
le copie `build\zx-0.N.exe` sono di allora. Al primo avvio [z]f sposta `%APPDATA%\zx` in
`%APPDATA%\z-f` e, quando si attiva o disattiva "Usa [z]f al posto di Explorer", toglie
l'integrazione del vecchio zx rimettendo i valori originali.

## Struttura del codice

Si compila un solo file, `src/z-f.cpp`, che include i moduli nell'ordine in cui dipendono l'uno dall'altro (*unity build*). I vantaggi: compilazione veloce, ottimizzazione su tutto il programma, nessun costo di collegamento. Ogni modulo comincia con una riga che dice cosa fa. Le dichiarazioni condivise sono in `app.h`.

| Modulo | Cosa contiene |
|---|---|
| `base.h` | include di sistema, misura del tempo, registro dei rallentamenti |
| `theme.h` | colori, misure e tempi dell'interfaccia con un nome per ognuno (regole d'uso in `DESIGN.md`) |
| `gfx.cpp` | D3D11: device, swapchain flip-model, shader, batch di quad (rettangoli, glifi, icone in un unico vertex buffer) |
| `text.cpp` | glifi rasterizzati con GDI al primo uso in un atlante R8, disegno del testo, casella di testo, appunti |
| `listing.cpp` | lettura delle cartelle su thread di lavoro, chiavi di ordinamento naturale |
| `zip.cpp` | archivi zip in sola lettura: directory centrale (zip64), albero delle cartelle in memoria, inflate e CRC nostri, estrazione su un thread |
| `lnk.cpp` | lettore dei collegamenti di Windows (.lnk), senza la shell; percorsi di rete di Windows |
| `app.h` / `app.cpp` | stato; layout, selezione, filtro, navigazione, ricariche |
| `dirsize.cpp` | dimensione totale delle cartelle su un thread (urgenti per tooltip e anteprima, coda di sfondo per la colonna), cache |
| `links.cpp` | colonna Destinazione dei collegamenti: destinazioni lette su un thread, cache, clic ("Apri percorso file") |
| `watch.cpp` | aggiornamento in tempo reale (`ReadDirectoryChangesW`), compresi spostamento ed eliminazione della cartella aperta |
| `icons.cpp` | icone della shell su un thread dedicato, atlante BGRA |
| `render.cpp` | disegno di un frame, pannelli sovrapposti (`drawPanel`) e pannello F12 |
| `shell.cpp` | menu completo della shell e comandi della shell (su un thread loro), appunti, rinomina nella riga |
| `fileops.cpp` | operazioni sui file su un thread (`IFileOperation` con l'esito di ogni elemento, rinomina, nuova cartella), cronologia per annullare e ripetere |
| `tabs.cpp` | schede: scambio dello stato, barra delle schede |
| `sidebar.cpp` | barra laterale: preferiti (file in `%APPDATA%\z-f`), unità e percorsi di rete, letti su thread separati |
| `integration.cpp` | [z]f al posto di Explorer: chiavi in HKCU, salvataggio e ripristino dei valori precedenti |
| `update.cpp` | aggiornamento automatico dalle Release di GitHub (WinHTTP, JSON, versioni, impronta e firma con CNG), scambio dell'exe, riavvio di tutte le finestre, icona di stato |
| `filedlg.cpp` | dialoghi Apri e Salva degli altri programmi nella cartella di [z]f (`SetWinEventHook`, campo del nome da un thread) |
| `settings.cpp` | impostazioni e salvataggio atomico in background dei file in `%APPDATA%\z-f` |
| `chrome.cpp` | cornice della finestra: barra del titolo con le schede, pulsanti, area non client |
| `crumbs.cpp` | percorso a segmenti cliccabili, menu delle sottocartelle |
| `tooltip.cpp` | tooltip: contenuto, informazioni lette su un thread (anche per l'anteprima), disegno |
| `preview.cpp` | pannello di anteprima: immagini (WIC), testo, cartelle, informazioni; lettura e decodifica su un thread |
| `thumbs.cpp` | vista a griglia: miniature (cache di Windows, WIC, shell, icone) su thread, atlante sulla GPU, vista per cartella (`viste.txt`) |
| `options.cpp` | pannello delle opzioni, tabella delle scorciatoie (anche per i menu), versione |
| `goto.cpp` | "Vai a": cartelle recenti (`recenti.txt`), ricerca fuzzy, sottocartelle lette su un thread, pannello |
| `drag.cpp` | trascinamento dei file: sorgente (oggetto dati della shell), destinazione (IDropTarget), rilascio alla shell su un thread |
| `zipout.cpp` | dallo zip verso fuori: aprire, copiare e trascinare con i file estratti su un thread in `%TEMP%\z-f` |
| `listmouse.cpp` | lista col mouse: selezione col rettangolo, colonne ridimensionabili (trascinamento, adattamento al contenuto) |
| `menu.cpp` | menu contestuale nostro (lista, voci della barra laterale, schede, applicazione) |
| `hybrid.cpp` | WARP all'avvio, poi passaggio alla GPU |
| `input.cpp` | tastiera, mouse, messaggi della finestra |
| `main.cpp` | avvio e ciclo dei messaggi |
| `z-f.rc` / `z-f.ico` / `risorse.h` | risorse dell'exe: l'icona, disegnata da `strumenti\icona.py`; gli ID, in comune con `base.h` |

Regola d'oro: **il thread dell'interfaccia non tocca mai il disco.**

## Avvio e rendering

Rendering **ibrido** (predefinito): il primo frame lo disegna WARP, il renderer software di Direct3D, che non deve caricare nessun driver. Intanto, su un altro thread, si inizializza la GPU, che su un PC di prova costa circa 140 ms. Quando è pronta, il programma passa alla GPU senza sfarfallio: disegna su una seconda finestra figlia posta sotto la prima, aspetta che il compositore mostri quel frame, poi rimuove la vecchia. Il thread della GPU parte solo *dopo* che WARP è pronto. Caricare le DLL del driver tiene occupato il loader lock di Windows, e farlo in parallelo bloccava WARP: misurato, da 25 a 98 ms. Valori misurati su RTX 5070 Ti: contenuto visibile a 70–81 ms, passaggio alla GPU intorno ai 200 ms. Su schermi grandi WARP da solo sarebbe troppo lento: circa 15 ms a frame a 2560×1369, contro 0,2 ms della GPU.

Opzioni di diagnostica: `--gpu=hw` (solo GPU, attende il driver), `--gpu=warp` (solo rendering software). Il pannello F12 mostra l'adattatore usato e i tempi di ogni fase.

Il passaggio WARP → GPU copia gli atlanti di glifi e icone dal device WARP, che vive nella RAM, a quello della GPU, invece di ricostruirli. Inoltre aspetta un momento tranquillo (al massimo 2 secondi) se in quel momento stai usando o trascinando la finestra.

## Le funzioni, una per una

- finestra Win32 con swapchain D3D11 in modalità flip e latenza di un frame;
- **icona** (`src\z-f.ico`, aspetto in `DESIGN.md`): una risorsa dell'exe (`src\z-f.rc`, con l'ID `ZF_ICON` in `src\risorse.h`, che includono sia il .rc sia `base.h`) compilata da `rc` in `build.bat` (da zig stesso in `build_zig.bat`). L'ico la scrive `strumenti\icona.py`, uno script Pillow usato una volta come `strumenti\firma.cpp`, che legge i due colori da `theme.h`: 16 e 20 px disegnate a pixel, le altre misure dalla stessa geometria agganciata ai pixel, disegnata a 4× e ridotta con una media esatta (BOX: niente aloni scuri). Sotto 256 le immagini sono BMP a 32 bit, il formato classico delle icone; la 256 è PNG, che lì pesa molto meno. La classe della finestra registra ancora l'icona generica di Windows: le due chiamate che caricano la nostra (`LoadImageW` alla misura grande e piccola del DPI della finestra) costano 1,3–2,7 ms e prima di `CreateWindowEx` ritardavano tutto l'avvio (misurato: 1,6–2,8 ms contro 0,0 dell'icona generica). Ora `appIconSet` (`chrome.cpp`) le carica dopo il primo frame, come `dropRegister`, e le dà alla finestra con `WM_SETICON`; di nuovo a ogni `WM_DPICHANGED`, liberando le vecchie. Il tempo dell'ultima volta è in F12 ("icona della finestra"); oltre `LOG_MSG` nel registro, "icona della finestra lenta". L'exe cresce di 46 KB (1.050.624 → 1.097.728 byte), quasi tutti dell'icona; il contenuto visibile resta lo stesso (`prove\avvio.bat`, 20 avvii alternati: mediana 52,5 ms prima, 52,9 dopo);
- tutto il testo disegnato dalla GPU, con un atlante di glifi rasterizzati da GDI al primo uso. Se Windows usa ClearType, i glifi sono in ClearType: tre coperture per pixel, una per subpixel, fuse con lo sfondo dallo shader con il dual-source blending (come il testo delle app di Windows); altrimenti scala di grigi con lo stesso percorso. Dimensione regolabile con Ctrl+rotellina, Ctrl +/−, Ctrl+0;
- **animazioni brevi e con uno scopo**: evidenziazione al passaggio del mouse che sfuma, cursore che scivola tra le righe, cartella nuova che entra in dissolvenza, icone che sostituiscono il segnaposto con una dissolvenza incrociata, menu e tooltip che compaiono in dissolvenza, indicatore della scheda attiva che scorre. Un solo meccanismo (avvicinamento esponenziale con costante di tempo nota); si ridisegna solo finché qualcosa si muove, poi zero CPU. Disattivabili con `animazioni=0`;
- **tooltip** dopo mezzo secondo fermi (60 ms passando tra elementi vicini): sui file nome completo, tipo, dimensione in byte, risoluzione delle immagini (letta dall'intestazione PNG/JPEG/GIF/BMP), date di modifica e creazione con il tempo trascorso, attributi, totale della selezione; sulle cartelle il contenuto (letto in background, al massimo 200 ms) e la dimensione totale con il numero di file, che cresce mentre si conta; sulle unità file system, capacità, usato e libero; su schede, pulsanti, intestazioni e barra dei tempi cosa fanno. Le informazioni dal disco arrivano da un thread e il tooltip le aspetta al massimo 150 ms, così compare già completo;
- impostazioni in `%APPDATA%\z-f\impostazioni.txt` (`dimensione`, `carattere`, `barra_laterale`, `barra_laterale_larghezza`, `barra_tempi`, `animazioni`, `colonna_data`, `colonna_dimensione`, `colonna_destinazione`, `anteprima`, `anteprima_larghezza`, `carattere_anteprima`, `annulla_dopo_riavvio`, `menu_completo`, `dimensione_cartelle`, `dialoghi`, `griglia_dimensione`, `riapri_schede`, `aggiornamenti`, `aggiornamenti_beta`, `aggiornamenti_ultimo`), modificabili anche a mano;
- **dimensione delle cartelle** (`dirsize.cpp`): un thread somma i file sotto una cartella senza seguire junction e collegamenti, come Explorer. Tooltip e anteprima lo chiedono subito (il totale si aggiorna ogni 100 ms mentre cresce, e si ferma se il mouse va altrove); la colonna Dimensione conta in background, con priorità di I/O bassa, le sottocartelle della cartella aperta nell'ordine della vista. I risultati restano in memoria per un minuto (con le sottocartelle dirette, così entrando ci sono già); una copia, uno spostamento, un'eliminazione o una ricarica li dimenticano prima. Le unità di rete e quelle ottiche si contano solo a richiesta (tooltip, anteprima): "unità lenta" lo decide una funzione sola (`slowPath`), la stessa che mette le cartelle di rete dopo le locali in "Vai a" e nelle miniature. Parte dopo il primo frame. Misurato: tutto C:\ (18 cartelle) in 14,4 s sul thread, con i frame a 0,12 ms (peggiore 0,35); opzione "Dimensione delle cartelle nella colonna";
- **dialoghi Apri e Salva degli altri programmi** (`filedlg.cpp`): entrano nella cartella aperta nell'ultima finestra di [z]f usata, appena si aprono e quando ci si torna dopo aver cambiato cartella in [z]f. Nessuna DLL negli altri processi: `SetWinEventHook` fuori contesto dice quale finestra passa in primo piano; se è un dialogo Apri o Salva (nuovo o classico), un thread scrive il percorso nel campo del nome, preme Apri/Salva (con una cartella il dialogo ci entra) e rimette il nome com'era. Aspetta che il dialogo sia pronto (la vista dei file con il suo elenco, più 150 ms): prima, provato, il comando fa cadere il programma in COMDLG32. La scelta di una cartella non si tocca (confermare la sceglierebbe). Con più finestre di [z]f agisce l'ultima usata (HWND in memoria condivisa). Misurato: notifica sul thread UI al massimo 0,14 ms, salto 290 ms sul thread (quasi tutto attesa del dialogo); opzione "Dialoghi Apri e Salva nella cartella di [z]f". Per provarlo: `prove\dialoghi-prova.cpp`;
- lista virtualizzata: si disegnano solo le righe visibili;
- lettura delle cartelle su un thread separato (`FindFirstFileExW` + `FindExInfoBasic` + `FIND_FIRST_EX_LARGE_FETCH`). Provata anche `GetFileInformationByHandleEx` con buffer da 1 MB: nessun guadagno misurabile, quindi è stata tolta;
- la finestra compare subito con lo sfondo del tema; il contenuto arriva con WARP e poi la GPU prende il posto di WARP (vedi "Avvio e rendering"). Se la GPU si perde (driver aggiornato o reimpostato), un thread crea un device nuovo e [z]f ricostruisce atlanti e texture invece di cadere: provato simulando la perdita, ripristino in 58 ms (36 sul thread dell'interfaccia);
- ordinamento naturale con chiavi precalcolate: ogni nome diventa una volta sola una sequenza di token da 16 bit (minuscole, accenti rimossi, numeri confrontati per valore), poi `memcmp`. Sostituisce `StrCmpLogicalW`;
- filtro mentre scrivi (sottostringa sui nomi già in minuscolo, preparati dal thread di lettura: 0,4 ms su 30k nomi), ordinamento per colonna, cronologia avanti/indietro;
- **icone vere**: due thread le chiedono alla shell (`SHGetFileInfo`). Quasi tutte si risolvono per estensione, senza toccare il disco; i tipi con un'icona propria per ogni file (exe, lnk, ico, url, ...) e le unità usano il percorso reale, e hanno un thread loro (partito alla prima richiesta): un collegamento su una condivisione scollegata non ferma più le icone di tutto il resto. Da dove viene l'icona (percorso vero, cartella o estensione) lo decide una funzione sola, `iconSource`, usata anche dalle miniature e dall'anteprima: i percorsi di rete di Questo PC hanno l'icona di cartella, senza chiedere niente alla rete (`iconDrive`; prima, in griglia e nell'anteprima, una condivisione lenta faceva aspettare 20 s l'icona sua e quelle delle unità in coda dietro, e passava la sua icona a tutte le cartelle). Il secondo thread aspetta che il primo abbia preparato le icone di sistema della shell: insieme, la prima chiamata falliva. L'alfa si ricava disegnando l'icona due volte, su nero e su bianco. Le icone vanno in un atlante BGRA sulla GPU, letto dallo stesso shader del testo: le UV con x ≥ 1 indicano l'atlante delle icone. Finché un'icona non è pronta si vede un segnaposto, e il thread UI non aspetta mai. Per la cache c'è anche una copia sulla CPU, così le icone si ricaricano quando si passa da WARP alla GPU;
- **selezione multipla**: la selezione è un flag per voce, quindi resiste a ordinamento, filtro e ricariche automatiche, che la ricostruiscono per nome. C'è un cursore separato dalla selezione e un'ancora per gli intervalli. Il filtro tiene le voci selezionate che restano visibili; se la selezione era di una sola voce, passa al primo risultato. La barra di stato mostra quante voci sono selezionate e quanto pesano;
- **menu contestuale nostro**, disegnato come il resto dell'interfaccia: si apre in circa 5 µs più un frame. Contiene solo le voci essenziali. Sui file: Apri, Apri con, Taglia, Copia, Copia percorso, Rinomina, Elimina, Proprietà. Sullo sfondo: Incolla, Nuova cartella (che parte già in rinomina), Aggiorna, Copia percorso, Apri terminale qui, Proprietà. "Altre opzioni…" (o Shift+clic destro, Shift+F10) apre il **menu completo della shell**, con tutte le estensioni installate: costruirlo costa 200–450 ms (la prima volta di più), per questo non è il menu predefinito. Lo costruisce e lo mostra un thread suo, con una finestra nascosta sua, mentre l'interfaccia continua a disegnare (`shell.cpp`); Elimina, Incolla, Rinomina, Copia e Taglia tornano a [z]f con i percorsi del momento del clic, quindi si annullano con Ctrl+Z come i tasti. Un clic o un tasto mentre il menu si costruisce lo annulla; nel registro "menu della shell lento" (oltre 50 ms, sul thread). Chi lo preferisce lo rende predefinito con l'opzione "Menu completo di Windows col tasto destro" (`menu_completo=1`): nella lista il tasto destro apre quello della shell e Shift+tasto destro il nostro. È sempre il menu classico con tutte le voci, perché il menu ridotto di Windows 11 esiste solo dentro Explorer: non serve nessuna modifica di Windows. In "Questo PC" il menu ha "Connetti unità di rete…" (sullo sfondo) e "Disconnetti" (su un'unità di rete). COM/OLE si carica solo al primo uso, quindi l'avvio non lo paga.
- comandi senza menu: Canc (Cestino), Shift+Canc (eliminazione definitiva, chiesta dalla shell), Ctrl+C/X/V, Alt+Invio (Proprietà). Shift+Canc, le Proprietà di più voci e Copia/Taglia di unità passano dalla shell sul thread del menu completo: preparare l'oggetto della shell costa circa 80 µs a voce in locale e 400 µs su una condivisione (20.000 file: 1,6 s e 8 s), e intanto l'interfaccia continua. Copia e Taglia non passano dalla shell: i percorsi sono già in memoria, quindi negli appunti vanno `CF_HDROP` e "Preferred DropEffect" senza toccare il disco (20.300 voci: 5,8 ms invece di 545). Uscendo, gli appunti vengono consegnati a Windows (`OleFlushClipboard`), così un "Incolla" fatto dopo funziona ancora. Dopo Taglia e Incolla gli appunti si svuotano, come in Explorer. Incolla funziona anche con elementi senza percorso, copiati da dentro uno zip, da un telefono o da un allegato: negli appunti non c'è `CF_HDROP` ma solo i formati della shell, e l'oggetto degli appunti va alla cartella come un rilascio (il suo `IDropTarget`, sul thread di Incolla), che li estrae;
- **annulla e ripeti** (`fileops.cpp`; Ctrl+Z, Ctrl+Y · Ctrl+Shift+Z, ≡ → "Annulla …" / "Ripeti …", menu dello sfondo → "Annulla …"): spostamenti (trascinamento, Taglia/Incolla), copie (le copie vanno nel Cestino), rinomine, cartelle nuove (vuote si rimuovono, altrimenti Cestino; creazione e rinomina subito dopo sono una voce sola), eliminazioni nel Cestino (ripristino dell'elemento esatto) e collegamenti creati. Spostamenti, copie ed eliminazioni passano da `IFileOperation`, il motore di copia di Explorer (stesse finestre di avanzamento, conflitti e permessi), su un thread; un `IFileOperationProgressSink` dà l'esito di ogni elemento: il nome finale dopo "Mantieni entrambi", gli elementi saltati e, per l'eliminazione, l'elemento esatto nel Cestino (`$R…`), che si rimette al suo posto togliendo anche il suo `$I…`. Prima di toccare un elemento il thread controlla il disco: se l'elemento non c'è più, se il suo posto è occupato, se la cartella è sparita, se una copia è stata modificata dopo o aveva sostituito un file, lo salta e lo dice ("Impossibile annullare lo spostamento: in Sorgente c'è già un elemento chiamato a.txt"); non sostituisce mai niente. Se invece il motivo può passare (file in uso, Annulla nella finestra della shell, permessi), gli elementi non riusciti restano in cima alla cronologia e il Ctrl+Z dopo riprova ("…; si può riprovare"). L'avviso dice sempre cosa è stato fatto e dove ("Annullata l'eliminazione: 5 elementi di nuovo in Download"). La cronologia è per finestra, 100 operazioni, solo in memoria; con l'opzione "Annulla dopo il riavvio" (spenta) si salva in `%APPDATA%\z-f\annulla.txt`. Elimina e Incolla del menu completo della shell passano da [z]f come i tasti, quindi si annullano; restano fuori Shift+Canc, le altre voci del menu della shell e gli elementi senza percorso (zip, telefoni, allegati), trascinati o incollati. Chiudendo [z]f durante un'operazione sui file la finestra sparisce subito, ma il processo esce solo quando l'operazione è finita (prima la interrompeva a metà); riaprendo [z]f nel frattempo torna la stessa finestra. Misurato: registrare un'operazione costa meno di un microsecondo; annullare l'eliminazione di 5 elementi 3,6 ms sul thread (mandarli nel Cestino 98 ms);
- **rinomina nella riga** (F2 o voce del menu) con una casella di testo vera: cursore, selezione, Ctrl+frecce, appunti (Ctrl+V legge il testo su un thread: chi possiede gli appunti può prepararli solo quando servono, e il thread dell'interfaccia lo aspetterebbe senza limite). Il nome è preselezionato senza estensione e lo spostamento avviene su un thread separato. La stessa casella serve anche per la barra del percorso;
- se il programma va in crash, scrive codice e indirizzo dell'errore in `z-f-crash.txt` accanto all'eseguibile;
- **registro dei rallentamenti** in `z-f-log.txt` accanto all'eseguibile, con l'ora di ogni evento: messaggi oltre 25 ms, frame con preparazione oltre 16 ms, attese del vsync oltre 34 ms, Present oltre 16 ms (il primo su una swapchain nuova della GPU, 15–30 ms per il driver, si chiama "primo Present GPU": è normale), oggetti e comandi della shell oltre 25 ms (che il conteggio dei messaggi non vede); le soglie sono in `theme.h` (`LOG_*`). Le righe vanno in una coda e le scrive un thread: il registro stesso non tocca il disco dal thread dell'interfaccia. Nel pannello F12 compaiono il messaggio più lento e l'attesa del vsync più lunga;
- **aggiornamento in tempo reale**: un thread osserva la cartella con `ReadDirectoryChangesW`. Le notifiche vengono raggruppate (al massimo una ricarica ogni 50 ms) e la cartella viene riletta in background, conservando selezione, scroll e filtro. Lo stesso thread osserva anche la cartella superiore: se la cartella corrente viene rinominata o spostata, la segue (`GetFinalPathNameByHandleW`); se viene eliminata o finisce nel Cestino, risale di un livello. Aprire e chiudere le cartelle osservate lo fa il thread: il thread dell'interfaccia non aspetta più (prima `CreateFileW` e un'attesa fino a 2 s, pesanti su una condivisione di rete). Misurato: circa 54 ms dalla notifica allo schermo; con 1000 file spostati in 12 s, 272 ricariche e nessun file perso;
- **schede**: ognuna conserva cartella, selezione, scroll, filtro, ordinamento e cronologia. Lo stato della scheda attiva vive nei campi di sempre, quindi il resto del codice non sa nulla delle schede: cambiare scheda scambia quei campi con quelli salvati (O(1), nessuna copia). Solo la scheda attiva è osservata dal watcher; quando una scheda torna attiva viene ricaricata in background. Una scheda lasciata a metà caricamento riprende il caricamento quando ci si torna. Le schede aperte in background dalla stessa scheda si accodano in ordine, come nei browser. La barra delle schede è sempre visibile: se comparisse alla seconda scheda, il contenuto salterebbe in basso proprio mentre si clicca;
- **barra laterale** con Preferiti e "Questo PC", con le unità rientrate sotto come nell'albero di Explorer (nome, spazio libero, barra d'uso: rossa oltre il 90%). La freccia a destra di Questo PC apre e chiude il ramo delle unità; chiuso, Questo PC mostra la pillola dell'unità su cui si trova la cartella aperta (menu di Questo PC: Apri, Apri in nuova scheda, Connetti unità di rete…, Proprietà, che apre Impostazioni › Sistema › Informazioni con `ms-settings:about` su un thread: sul thread dell'interfaccia costava 222 ms). Evidenzia la cartella corrente e l'unità su cui si trova. Le unità di rete hanno il nome della condivisione come in Explorer ("Condivisione (G:)", o quello dato dall'utente: `SHGetFileInfo`), non l'etichetta del disco sul server, che spesso è la stessa per tutte; `\\server\condivisione` sta nel tooltip (`WNetGetConnection`) e il loro menu ha "Disconnetti". Chiede all'API pubblica di GitHub le ultime 10 Release (senza login: 60 richieste l'ora per indirizzo, ne serve una al giorno) con WinHTTP, che si carica solo lì (`/DELAYLOAD`), con il proxy del sistema e tempi massimi di 10 s (30 s per leggere). Un lettore JSON nostro tiene solo `tag_name`, `prerelease`, `draft`, `html_url` e i file. Sceglie la versione più alta del canale (Semantic Versioning: `1.0.0-beta.2` < `1.0.0-beta.10` < `1.0.0-rc.1` < `1.0.0`) più nuova di quella in uso; se c'è, scarica in memoria `z-f-<versione>.exe` e `z-f-<versione>.exe.sig`, e controlla dimensione, impronta SHA-256 (il `digest` che GitHub dà per ogni file) e firma ECDSA P-256 con la chiave pubblica che [z]f contiene (CNG, `bcrypt.dll`, anche lei a caricamento ritardato). La chiave privata sta solo sul PC di chi pubblica, cifrata con DPAPI (`strumenti\firma.cpp`): chi entrasse nell'account GitHub non potrebbe distribuire un exe che [z]f accetta. Poi lo scambio, sullo stesso disco: `z-f.exe.nuovo` accanto all'exe, `z-f.exe` → `z-f.old.exe` (Windows permette di rinominare un exe in esecuzione), `z-f.exe.nuovo` → `z-f.exe`; se il secondo passo fallisce si rimette il primo. Il percorso non cambia, quindi "Usa [z]f al posto di Explorer" e i collegamenti continuano a funzionare. Se la cartella non è scrivibile, o la Release non ha l'exe firmato, l'avviso dice che c'è una versione nuova e un clic apre la sua pagina. Un'altra finestra che controlla dopo lo scambio trova già sul disco l'exe giusto (`z-f.old.exe` c'è e l'impronta di `z-f.exe` coincide) e non scarica di nuovo. Mai su un exe in rete (lo scambio lo farebbe la rete, a metà) né nelle build compilate con `ZF_DEV` (`build_zig.bat`). Il thread dell'interfaccia riceve solo il risultato (`WM_APP_UPDATE`, con un contatore di generazione). "Aggiorna" manda alle altre finestre di [z]f un messaggio registrato (`z-f.riavvio`): ognuna salva le sue schede in `riavvio-<pid>.txt` e la sua posizione, si chiude (con operazioni sui file in corso aspetta che finiscano, come sempre) e, uscendo, si riavvia con `--riavvio=<pid> --finestra=…` (`--principale` per quella che riceve le cartelle da fuori, che tiene anche il mutex dell'istanza unica). Al primo frame la versione nuova cancella `z-f.old.exe` su un thread e dice "Aggiornato a [z]f …". Per le prove, `--aggiorna-da=<url>` usa un server locale (`<url>/releases.json`) al posto di GitHub, e il controllo parte dopo 2 s anche in una finestra secondaria. Misurato con un server locale: controllo 18 ms, download dell'exe e della firma 25 ms, tutto sul thread; con il server spento l'errore arriva dopo 2 s, sempre sul thread.

Il programma non usa CPU quando non c'è niente da fare: ridisegna solo dopo un input o durante lo scorrimento animato.

## Compilare: MSVC e zig

Lo script trova da solo `cl.exe` tramite `vswhere`. Se nel PATH c'è anche `fxc.exe` (incluso nel Windows SDK), gli shader vengono precompilati e l'avvio è più rapido. Altrimenti vengono compilati all'avvio, e la barra di stato lo segnala. L'icona (`src\z-f.rc`) la compila `rc.exe`, anche lui del Windows SDK, in `build\z-f.res`, che va al link con il resto.

**Senza Visual Studio:** `winget install zig.zig`, poi `build_zig.bat`, che scrive `build\z-f-dev.exe` (la build di prova) e non tocca `build\z-f.exe`. Usa gli shader precompilati se `build.bat` li ha già prodotti in `build\`.

La build consigliata è quella MSVC. Confronto misurato sullo stesso codice e sulla stessa cartella (WinSxS, 30k voci):

| | MSVC | zig |
|---|---|---|
| eseguibile | 324 KB | 668 KB |
| shader | precompilati (0 ms) | compilati all'avvio (circa 4 ms) |
| ordinamento 30k nomi | 4,3 ms | 7,5–8 ms |
| contenuto visibile | 67–73 ms | 69–81 ms (differenza nel rumore) |

Con MSVC, `shell32` e `ole32` si caricano solo al primo uso (`/DELAYLOAD`). Sul tempo di avvio misurato non cambia nulla di rilevabile, ma la finestra non carica due DLL che non le servono.

## Controllo prima del push

`.githooks/pre-push` (attivo con `git config core.hooksPath .githooks`, una volta per copia del repository; solo `sh`, `git`, `grep` e `sed` di Git for Windows) fa due controlli:

- **main:** blocca il push diretto su `main`, che si aggiorna solo con una pull request da `dev`;
- **dati da non pubblicare:** il repository è pubblico. Per ogni ref in uscita prende i commit che il remoto non ha (`remote_sha..local_sha`; per un branch nuovo, quelli che nessun branch del remoto contiene) e di ciascuno guarda solo ciò che è nuovo: righe aggiunte del diff (contro il primo genitore), messaggio, nomi dei file, nome e email di autore e committer. Blocca le email che non sono quelle anonime di GitHub (`…@users.noreply.github.com`, `noreply@github.com`), i percorsi della cartella di un utente (`X:\Users\…`, `X:/Users/…`, anche con le barre raddoppiate dei sorgenti, e `/x/Users/…` di Git Bash; ammessi `utente`, `Public`, `Default` e i segnaposto come `<nome>`), i file `.exe`, `.sig`, `.bin`, `.pfx`, `.pem`, `.key`, `.p12` e le parole di `.git/info/parole-private.txt` (una per riga, `#` per i commenti; come parole intere, con `grep -w`, e senza distinguere maiuscole, così un nome non scatta dentro un'altra parola). Quel file sta in `.git`, quindi non si pusha mai, e l'hook, che è pubblico, non contiene nessuna parola privata; se manca, l'hook avvisa e non blocca. Ogni segnalazione dice commit, file e riga (o messaggio, nome di file, email); il messaggio finale chiede di correggere i commit (`git commit --amend`, `git rebase -i`).

Il diff si percorre riga per riga in `sh` (lento) solo se un `grep` su tutto il diff trova già qualcosa. Misurato: un commit 0,7 s; tutta la storia pubblica (6 commit, il primo con tutto il codice) 2,9 s; il caso peggiore, una parola trovata nel primo commit, 4,9 s. Le prove sono in un repository finto con un remoto nudo locale (21 casi, tutti passati).

## Differenze note rispetto a Explorer

L'ordinamento naturale qui è ordinale, con minuscole e accenti piegati. Explorer usa invece le regole linguistiche di Windows. Nei casi comuni il risultato è uguale (numeri, maiuscole/minuscole, lettere accentate). Può differire sui segni di punteggiatura: ad esempio Explorer tende a ignorare il trattino in "co-op".
